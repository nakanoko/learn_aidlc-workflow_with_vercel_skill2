## 1. 技術スタック要件

- フロントエンドは React を使用すること。
- バックエンドは Next.js の Route Handlers または API Routes を使用すること。
- フロントエンドとバックエンドは、原則として別コンテナで起動できる構成にすること。
- ローカル開発環境は docker-compose で起動できること。
- 各コンテナの起動手順、環境変数、確認方法を README に記載すること。

補足:

- Next.js をフロントエンド兼BFFとして利用する場合は、その理由と構成を設計書に明記すること。
- フロントエンドとバックエンドを完全に分離する場合は、API仕様と通信方式を明記すること。

## 2. 開発プロセス要件

- 処理高速化のため、合理的に必要な範囲でサブエージェントを立て、並列で作業すること。
- サブエージェントを立てる場合は、各エージェントの役割、入力、出力、完了条件を明確にすること。
- サブエージェントは必要最小限とし、原則として以下の役割から選定すること。
  - 要件整理エージェント
  - 設計エージェント
  - 実装エージェント
  - テスト作成エージェント
  - レビューエージェント
  - 修正エージェント

## 3. レビュー分離要件

- 設計・製造を担当するエージェントと、レビューを担当するエージェントは別ロールとして扱うこと。
- レビューエージェントは、設計・製造エージェントの判断を前提にせず、第三者の立場でレビューすること。
- レビュー時は、以下の観点を必ず確認すること。
  - 要件を満たしているか
  - 設計に矛盾がないか
  - 実装が設計と一致しているか
  - テストが十分か
  - セキュリティ上の問題がないか
  - 保守性・可読性に問題がないか
  - コンテナ構成が妥当か
  - READMEの手順で再現可能か

## 4. レビュー・修正ループ要件

- 各ステージでレビューを実施すること。
- レビュー指摘がある場合、設計・製造エージェントは指摘内容を確認し、修正方針を明記したうえで修正すること。
- 修正後、レビューエージェントが再レビューすること。
- レビュー指摘がなくなるまで、修正と再レビューを繰り返すこと。
- ただし、同一ステージで3回レビューしても重大な指摘が残る場合は、作業を停止し、人間に判断を仰ぐこと。
- 人間に相談する場合は、以下を提示すること。
  - 残っている指摘
  - 原因の推定
  - 対応案
  - 各対応案のメリット・デメリット
  - AIとして推奨する対応

## 5. 品質ゲート要件

作業完了前に、以下を確認すること。

- ビルドが成功すること。
- テストが成功すること。
- Lintまたは静的解析が成功すること。
- 型チェックが成功すること。
- docker-compose でローカル起動できること。ホスト側でDockerが反応しなかった場合、起動 or インストールするよう人間に案内すること。
- READMEの手順だけで第三者が起動確認できること。
- レビュー指摘がゼロ、または人間判断待ちの状態であること。
- package.json だけでなく package-lock.json も生成されていること
- READMEの構築手順は npm ci を前提にすること
- Dockerfileでは npm ci を使用すること
- npm ci が成功することを確認すること
- package.json と package-lock.json に不整合がないこと

## 6. 出力形式要件

最終回答では、以下の形式で報告すること。

1. 実施内容の概要
2. 作成・変更したファイル一覧
3. 設計上の判断理由
4. テスト結果
5. レビュー結果
6. 未解決事項
7. 人間が確認すべきポイント
